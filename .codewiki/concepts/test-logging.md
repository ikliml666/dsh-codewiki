## Overview

`test-logging` 是跨模块概念，覆盖 `dsh-codewiki` 插件的测试执行（由 [[test-scripts]] 模块驱动）、核心逻辑验证（针对 [[core-and-config]] 模块的 `index.js`）以及运行期日志产出（落盘于 [[logs-and-temp]] 模块）。该概念描述五个端到端测试脚本如何通过自带的 `check` 断言函数（`test-cwd-paths.mjs` 除外——它直接打印 `PASS`/`FAIL` 行；以及 `test-wiki-anchors.mjs` 的落盘后扫描）验证插件导出的纯函数与后台服务阶段机，并把分组断言结果打印到 stdout（历史上被重定向进对应的 `.tmp-test-*.log`），同时由外部 watcher 进程以约 30ms 间隔轮询 `index.js` 持久化的 `JOBS_FILE` 并追加到 `watcher2.log`，从而形成一套测试日志闭环。

当前阶段机由 `index.js` 的 `STAGE_HANDLER`（`index.js:3482-3489`）定义：`articles → crosscut → compose → review → index → commit`，外加占位态 `submitting`（`index.js:3579`，`submit` 先落占位、校验期间 tick 跳过）、排队态 `queued`（`index.js:3671`，项目闸门满时由 `submit` 置入）、终态 `done/failed/cancelled`（`JOB_TERMINAL` 集合在 `index.js:2104`，由 `fail`/`setStage` 直接置位）。其中 `compose` 是横切合成态（`tickCompose` 在 `index.js:3184-3196`）、`commit` 是 0.10.11 起独立出来的自动提交态（`tickCommit` 在 `index.js:3465-3481`）；旧的独立规划阶段已在 0.10.7 删除——`tickArticles` 在 articles 阶段就地生成模块清单（`index.js:2879` 起，其中 `scanRepoFiles` 在 `index.js:2992` 与 `buildPlan` 在 `index.js:2994` 就地规划——目录分组走 `localPlan`（`index.js:1300-1313`）），旧磁盘任务残留的 `stage:'plan'` 由 `tick` 的迁移分支（`index.js:3491-3499`）落到 articles。

注意：`.tmp-test-*.log` 与 `watcher2.log` 都是旧版本代码跑出来的落盘快照——本次核对的仓库快照中，五份 `.tmp-test-*.log` 已不存在（它们本就是把测试 stdout 重定向进固定文件名的临时产物，当前测试脚本一律 `console.log` 到 stdout、重跑不会重建），`watcher2.log` 仍在仓库根但本次未随源码内联；历史快照里记录的预算数值、阶段名、失败项与报错文案已与当前源码不同（详见 Implementation Map 的时效标注）。另外 `test-batch.mjs` 与 `test-orchestration.mjs` 本次也未随源码内联，文中涉及这两个脚本的条目只保留定性描述、不作行号核对。

## Involved Modules

1. **test-scripts**：包含 `test-batch.mjs`、`test-cwd-paths.mjs`、`test-orchestration.mjs`、`test-wiki-anchors.mjs`、`test-wiki-entry.mjs` 五个独立脚本。其中 `test-batch.mjs`、`test-orchestration.mjs`（`await import('./index.js')` 取得 `name/apply/SESSIONS_DIR`）、`test-cwd-paths.mjs`（`test-cwd-paths.mjs:20` 的 `import * as plugin`、`test-cwd-paths.mjs:20` 调 `apply(ctx, {})`）、`test-wiki-entry.mjs`（`test-wiki-entry.mjs:13` 导入被测导出）直接加载被测插件主体；`test-wiki-anchors.mjs` 不 import 插件，而是把 `index.js`/`client.js` 按「工作区 ∪ HEAD ∪ 编译基线」三个基准视图读入（`test-wiki-anchors.mjs:96-118` 的 `loadSource`、`test-wiki-anchors.mjs:119-122` 的 `SOURCES`），并用 `walk` 收集 `.codewiki/` 下全部 `.md`（含本文）做行号锚点核对（`test-wiki-anchors.mjs:213-222` 定义 `walk`、`test-wiki-anchors.mjs:224` 收集文章、`test-wiki-anchors.mjs:232-277` 执行核对）。各脚本自带 `check` 断言辅助（`test-wiki-anchors.mjs:172-176`、`test-wiki-entry.mjs:75-76`；test-batch/test-orchestration 同样自带 `check`）输出 `✓`/`✗`；`test-cwd-paths.mjs` 不用 `check`，直接打印 `PASS`/`FAIL` 行（MSYS PASS 在 `test-cwd-paths.mjs:45`、Windows PASS 在 `test-cwd-paths.mjs:57`、nonexistent 干净报错 PASS 在 `test-cwd-paths.mjs:68`，最终 `ALL PASS` 在 `test-cwd-paths.mjs:71`）。

2. **core-and-config**：提供插件核心 `index.js`（插件入口 `apply` 在 `index.js:4817-4881`，编排服务工厂 `createJobService` 在 `index.js:2295-3707`，阶段处理器表 `STAGE_HANDLER` 在 `index.js:3482-3489`，提交入口 `submit` 在 `index.js:3579-3680`），导出被验证的纯函数与服务化阶段机，并通过 `JOBS_FILE`（`index.js:1876`）与 `TICK_MS`（`index.js:1877`）驱动任务持久化与 tick 推进（默认 10s，下限 250ms）；测试通过 `DSH_CODEWIKI_TICK_MS=300` 与带随机 token 的独立 `DSH_CODEWIKI_JOBS_FILE`（文件名追加随机串，避免 pid 复用时读入历史 fixture 任务）把 tick 压到 300ms 并隔离到独立 jobs 文件，避免与真实宿主服务实例（同机共享默认路径）互相洗写；服务侧另有 `DSH_CODEWIKI_SESSION_TIMEOUT_MS`（`index.js:1881`）与 `DSH_CODEWIKI_ORPHAN_TAKEOVER_MS`（`index.js:2069`）两个可覆盖阈值。0.13.0 起新增三档「吸收自 FSoft CodeWiki」的能力——语义规划（`planMode`，默认 `'auto'` 即 AST 符号提取 + LLM 语义聚类、失败自动降级目录分组，见 `index.js:86`）、agentic 写作（`agenticArticles`，`index.js:87`，分派在 `tickArticles` 内调用 `startAgenticRun` 在 `index.js:2676-2726`）、符号级增量（`symbolIncremental`，`index.js:89`）——三者默认全开，但 `test-orchestration.mjs` 的基线 `LEGACY_CHANNEL` 把 `planMode` 钉成 `'dirs'`、`agenticArticles`/`symbolIncremental` 关掉，让编排冒烟继续守护旧通道的请求次数、装填方式与落盘时序。

3. **logs-and-temp**：纯日志数据模块，由 `.tmp-test-batch.log`、`.tmp-test-cwd-paths.log`、`.tmp-test-orchestration.log`、`.tmp-test-wiki-anchors.log`、`.tmp-test-wiki-entry.log` 及 `watcher2.log` 组成，承接测试断言的 stdout 重定向输出与 watcher 轮询输出；仓库内没有直接写这些文件的代码（当前测试脚本直接 `console.log` 到 stdout），它们是运行测试/watcher 时捕获的落盘快照——其中五份 `.tmp-test-*.log` 在本次核对的仓库快照中已不存在，仅 `watcher2.log` 仍在仓库根。插件真正的运行期日志只有两处：job 的 `notes` 追加（`index.js:2375-2378` 的 `note()`，随 `index.js:2199-2204` 的 `saveJobs` 落盘——`watcher2.log` 里的 `notes=` 计数即来源于此）与会话内容记录（`index.js:1984-2026` 的 `beginSessionRecord` 写 `SESSIONS_DIR`（`index.js:1893`），保留一天、由 `index.js:3497-3499` 的 `tick` 周期调用 `pruneSessionRecords`（`index.js:1952-1972`）清理）。

## Flow

1. **加载与执行**：测试脚本启动即加载 `core-and-config` 的插件主体（`test-wiki-entry.mjs:10`；`test-cwd-paths.mjs:20` 导入后 `test-cwd-paths.mjs:20` 调 `apply(ctx, {})` 注册工具；`test-batch.mjs`/`test-orchestration.mjs` 同样导入插件主体，本次未随源码内联）；`test-orchestration.mjs` 导入前先写 `DSH_CODEWIKI_TICK_MS=300` 与带随机 token 的独立 `DSH_CODEWIKI_JOBS_FILE`，收尾统一删除不留残留。
2. **断言与逻辑验证**：脚本用 `fs.mkdtempSync` 构造临时仓库（`test-orchestration.mjs` 的 `makeFixtureRepo` 还会 git init 并配置 git identity，因为 `autoCommitWiki` 在缺 user.name/user.email 时拒绝自动提交——identity 检查在 `index.js:301-303`）；纯函数直接调用断言（如 `ensureWikiEntry` 由 `test-wiki-entry.mjs:18` 验证，`fixAnchors` 全套用例与会话通道收割三态由 `test-batch.mjs` 验证）；编排链路则通过 `makeCtx` 注入 mock 的 webServer/tools/agents/llm 服务（`llmProxy` 转发到 `activeLlm`）后执行 `apply(ctx, cfg)`，再触发 `gen.execute`（全量编译与 stale 更新），测试侧以 `waitJob` 轮询 `JOBS_FILE`（终态集合 done/failed/cancelled，与 `index.js:2104` 的 `JOB_TERMINAL` 一致）等待 `createJobService` 阶段机推进到终态（该脚本本次未内联，不作行号核对）。
3. **测试日志落盘**：测试执行进程把分组断言结果按固定文本格式打印到 stdout（可直接核对的汇总行：`test-wiki-anchors.mjs:402` 的 `锚点校验：${passed} 过 / ${failures} 败`、`test-wiki-entry.mjs:75` 的 `全部断言通过`、`test-cwd-paths.mjs:71` 的 `ALL PASS`；test-batch/test-orchestration 各有类似汇总行与 exit code）。五份 `.tmp-test-*.log` 不是当前脚本直写的——它们是历史运行把 stdout 重定向进这些文件名得到的快照（当前仓库快照中已不存在）；当前脚本只是把同样文本打到 stdout，是否落盘 `.tmp-test-*.log` 取决于运行者是否重定向。
4. **Watcher 监听记录**：外部 watcher 进程以约 30ms 间隔轮询 `index.js` 落盘的 `JOBS_FILE`，把单行状态（含 `mtime`、job id、`stage`、`cancelReq`、`upd`、`notes` 计数）追加到 `watcher2.log`（历史快照，本次未随源码内联、无法逐行核对）；日志里可见 job 出现/notes 变化的瞬间与 mtime 跳变——`notes=` 计数来源于 `index.js:2375-2378` 的 `note()` 随 `index.js:2199-2204` 的 `saveJobs` 落盘。
5. **事后审查**：开发者读取日志获知失败总数与失败项、锚点偏差以及 job 停留在某阶段的现象。历史快照里的典型线索：旧格式 `source` 标记断言失败（当前插件所有模型调用与 steer 的 source 标记统一为 `plugin:codewiki`，见 `index.js:473` 与 `index.js:856`）、符号绑定不命中的锚点（正是行号漂移的证据，也是落盘前用 `fixAnchors`（`index.js:856-1073`）自动校正的动机）以及 job 长期停留在已删除的 `plan` 阶段（现由 `index.js:3553-3561` 迁移到 articles）。

```text
┌──────────────────┐  import/apply + gen.execute  ┌────────────────────────────────┐
│ test-scripts     │ ───────────────────────────► │ core-and-config                │
│ (test-*.mjs)     │   waitJob 轮询 JOBS_FILE     │ index.js 阶段机 articles→      │
└────────┬─────────┘                              │ crosscut→compose→review→       │
          │ check ✓/✗（stdout 打印）               │ index→commit（index.js:3482）  │
          ▼                                        └─────────────┬──────────────────┘
┌──────────────────┐                                            │ job 状态落盘
│ .tmp-test-*.log  │                             ┌──────────────▼─────────────────┐
│ （stdout 重定向） │                             │ JOBS_FILE → watcher2.log       │
└────────┬─────────┘                             │ （~30ms 轮询单行状态）         │
          │                                       └──────────────┬─────────────────┘
          └─────────── 事后审查：失败项 / 锚点偏差 / 卡阶段 ──────┘
```
